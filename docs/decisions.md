# ВЖИК — Architecture & Product Decisions Log

Формат: проблема → чому це проблема → запропоноване рішення → чи потрібне product decision.

> **Phase 1 Authorization**: усі відкриті питання нижче закриті рішеннями з `vzhyk_phase1_decisions.md`. Статуси оновлено, ⚠️ знято. Phase 0 Discovery завершено, проект переходить у Phase 1 — Foundation.

## DEC-01: «Житло подобово» — окрема категорія чи підкатегорія?

**Проблема**: вихідний документ ставить «Подобова оренда» підкатегорією «Нерухомості». Фактична структура olx.ua (перевірено серпень 2026) виносить «Житло подобово» окремим top-level розділом.
**Чому важливо**: користувацькі очікування і SEO-трафік на цю категорію суттєво відрізняються від звичайної оренди (інша аудиторія, інша форма оголошення — bookable dates замість терміну оренди).
**Пропозиція**: винести в окрему top-level категорію вже в MVP, з окремим набором атрибутів (дати заїзду/виїзду — підготувати поле, без календаря бронювання в MVP).
**Статус**: не впливає суттєво на бізнес-логіку → прийнято самостійно, зафіксовано тут. Якщо продукт не погоджується — легко відкотити (просто інша категорія в дереві).

## DEC-02: Category-specific модерація (Робота / Нерухомість)

**Проблема**: вихідний документ описує єдиний generic moderation pipeline, але вакансії потребують перевірки на дискримінаційні формулювання (вік/стать/сімейний стан — заборонено ЗУ «Про зайнятість населення»), а нерухомість — на правовстановлюючі документи.
**Чому важливо**: юридичні ризики для платформи, якщо цього немає навіть у мінімальному вигляді.
**Пропозиція**: MVP — generic pipeline + окремий список заборонених словосполучень для категорії «Робота» (проста rule-based перевірка, не окремий підмодуль). Повноцінні category-specific правила — Phase 2.
**Рішення (Phase 1 Authorization)**: для MVP окрема глибока category-specific модерація для «Робота» та «Нерухомість» **не реалізується**. Використовується загальна система модерації (generic pipeline з `moderation.md`). Спеціалізовані правила (дискримінаційні формулювання у вакансіях, перевірка правовстановлюючих документів) — Phase 2.
**Статус**: ✅ Вирішено.

## DEC-03: Видалення категорії з активними оголошеннями

**Проблема**: не описано, що відбувається з оголошеннями при видаленні/переміщенні категорії з Admin Panel.
**Пропозиція**: заборонити видалення категорії, поки в ній є активні (не архівовані/не видалені) оголошення; переміщення категорії дозволене, атрибути валідуються заново для нової позиції в дереві.
**Статус**: технічне рішення, не впливає на продукт → прийнято самостійно.

## DEC-04: Термін зберігання персональних даних

**Проблема**: вихідний документ не визначає retention policy для телефону, геолокації, історії чату після видалення акаунта.
**Чому важливо**: відповідність ЗУ «Про захист персональних даних», потенційно GDPR для користувачів-нерезидентів.
**Пропозиція**: soft-delete акаунта → анонімізація PII (телефон/ім'я/email) через N днів (запропоновано 30), збереження знеособлених даних для аналітики/юридичних вимог довше.
**Рішення (Phase 1 Authorization)**: retention period = **6 місяців** з моменту видалення акаунта (не 30 днів, як пропонувалось раніше). Протягом цього періоду персональні дані фізично зберігаються, але:
- не використовуються у звичайних користувацьких сценаріях (профіль, пошук, чат тощо);
- по завершенню 6 місяців — автоматизований cleanup/anonymization job;
- audit records не видаляються без необхідності (зберігаються довше, якщо потрібні для безпеки/юридичної історії, окремо від звичайних PII-полів).
**Статус**: ✅ Вирішено.

## DEC-05: Ліміти на кількість оголошень і частоту публікації

**Проблема**: не визначено ліміт активних оголошень / нових оголошень на добу для звичайного користувача — критично для навантаження на модерацію і anti-fraud.
**Пропозиція**: стартовий ліміт 20 нових оголошень/добу на користувача (rate limit, див. `api.md`), без ліміту на кількість активних (крім спам-детекції через RiskSignal). Ліміти конфігуруються в Admin Panel, не хардкодяться.
**Рішення (Phase 1 Authorization)**: для звичайного користувача діє ліміт **максимум 5 ACTIVE listings одночасно** (не ліміт на добу). Оголошення у статусах `SOLD`, `EXPIRED`, `ARCHIVED`, `BLOCKED` не займають слот активного оголошення. Ліміт конфігурується через Admin Panel (не хардкодиться). У майбутньому — диференційовані ліміти для звичайних/verified users/business accounts/платних тарифів.
Це доповнює, а не замінює, окремий rate limit на *створення* оголошень (`/listings` create — 20/добу на користувача, див. `api.md`/`security.md`), який лишається як anti-spam захист, незалежний від ліміту активних оголошень.
**Статус**: ✅ Вирішено.

## DEC-06: Модель зберігання ListingAttributeValue

**Проблема**: вихідний документ вимагає гнучку модель `Category → Attribute → Listing Attribute Value`, але не уточнює, чи зберігати типізовані колонки (`value_text/value_number/...`) чи єдину JSONB-колонку.
**Пропозиція**: єдина JSONB-колонка `value` з валідацією на рівні застосунку проти `category_attributes.data_type` — простіше в підтримці, достатньо для MVP-масштабу; типізовані колонки додати пізніше, якщо знадобляться складні SQL-агрегації по атрибутах.
**Статус**: технічне рішення → прийнято самостійно, задокументовано в `database.md`.

## DEC-07: Монетизація виключена з MVP — ризик конкурентності

**Проблема**: OLX монетизує через платні пакети розміщення й TOP/VIP оголошення; повна відсутність монетизації в MVP «Вжик» — свідомий вибір з вихідного документа, але варто зафіксувати ризик.
**Пропозиція**: залишити як є (відповідно до документа), архітектура вже готова (`PaymentProvider`) для швидкого додавання Phase 2+ без переробки core domain.
**Статус**: не потребує рішення зараз — вихідний документ явно це визначив, ризик задокументовано.

## DEC-08: AI / стороння content-moderation для тексту

**Проблема**: чи потрібен окремий AI/content-moderation сервіс (сторонній платний API) для перевірки текстових описів оголошень у MVP.
**Рішення (Phase 1 Authorization)**: у MVP окремий AI/content-moderation сервіс для тексту **не використовується**. Застосовується: rule-based validation, базові security checks, стандартна moderation system (`moderation.md`), ручна модерація там, де передбачена, user reports. Архітектура (провайдер-абстракція) повинна дозволяти додати AI moderation пізніше без значної перебудови системи.
**Статус**: ✅ Вирішено.

## DEC-09: Accessibility / WCAG для MVP

**Проблема**: вихідний документ не визначав вимоги до accessibility; впливає на дизайн-систему з самого початку Phase 1.
**Рішення (Phase 1 Authorization)**: у MVP реалізується **базова accessibility** (не повний WCAG audit/сертифікація): семантичні HTML-елементи, коректні labels для form fields, `alt` для значущих зображень, keyboard navigation, visible focus states, достатній color contrast, доступні кнопки/контроли, зрозумілі повідомлення про помилки, доступні modal/dialog компоненти, коректна структура заголовків, базова підтримка screen readers. Повний WCAG 2.1 AA audit — наступний етап (Phase 2+).
**Статус**: ✅ Вирішено.
